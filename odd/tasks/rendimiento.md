# Performance: the whole app fast

Objective: every screen loads and switches fast from the iPhone in Argentina; first the Gráficos section (measured), then every other page (audit pending).
Branch `feat/performance` from `feat/chart-mobile` 2d38b00 (both unmerged; same chart files). Delivery: stacked after `feat/chart-mobile`. Tests: vitest (`npx vitest run`), `npx tsc --noEmit`, `npm run lint`; before/after timings with the production-build probe of L3.

## Specs

- S1 "cada vez que entro o cambio de activo, tarda en cargar y tamb los dibujos ya olertas": opening Gráficos on an asset (`/trading?symbol=X`) loads only X; today it loads the last asset first (candles, alerts, drawings, quote), then X (L3).
- S2 The drawings of an asset arrive in one round trip: today an asset with no saved drawings asks again for the old format, in sequence, on every visit (L3).
- S3 Drawings and alerts never wait on a second request (S2) and an asset seen recently never shows "Cargando…" (S4). Decided by me (L4): the previous chart does not stay on screen while a new asset loads, since its candles would sit under the new asset's drawings.
- S4 An asset and timeframe seen recently opens at once from memory and refreshes behind; the server keeps candles longer than 30 s without staling the live bar; a ticker Yahoo does not know is not retried.
- S5 No duplicate requests on the chart page (`/api/positions` two or three times, `/api/quote` twice).
- S6 "quiero que lo optimices, que ande bien tapido, todo el proyecto en si, Busquemos maneras d emejoar el rendmiento": the same audit and fixes for every other page (L5). Decided by me from the audit: S7-S10; not done: verifying the session locally instead of asking Supabase Auth per request (a security trade-off for the user to decide) and moving pages to server components (a rewrite).
- S7 Shell, Resumen, Historial, Caja (client): changing section never asks for the portfolio again (the Ctrl+K search asks for held tickers when it opens, through `getPortfolio`/`POSITIONS_KEY` of `src/lib/warren/positions.ts`); Resumen's value chart and movements start with the page instead of after the summary; a page seen before in the tab shows its last data at once and refreshes behind (`src/lib/client-cache.ts`); Historial's tabs keep what they loaded; the market-hours countdown re-renders only itself; an edit or delete in Caja shows its result without a second round trip when the API can return it.
- S8 Server (response shapes unchanged): `/api/positions` on a summary miss runs its independent reads together, reuses the ledger it already read for the currency views, and leaves the summary in Redis guarded like the derived series (so evenings and weekends stop rebuilding it per request); the dollar rates answer from the last known value and refresh behind; the derived series is built once at a time per user and its independent reads run together; the statistics routes run their independent reads together and read ON quotes Redis-first; benchmark bars are cached like holding bars; the CEDEAR and asset catalogs carry a private cache header.
- S9 Estadísticas, Estrategias, ONs (client and their edit routes): recharts loads only with the chart that needs it; Estadísticas shows each block as its request answers and does not refetch history per tab or period when it can cut it in the browser; a page seen before in the tab shows its last data at once; Estrategias' performance page does not fetch the strategy only for its name and asks paper trades in one request; editing a test portfolio item or a payment returns the updated view (one round trip).
- S10 Every change keeps today's numbers: same API response shapes and values, the existing tests pass, and before/after timings are measured with the L3 probe.

- L3: measured. The app is in Ashburn VA (ipinfo), Supabase us-east-1: server↔DB is near and the user's data is small (6 drawing sets, 5 alerts). From Argentina every request to the app costs ~170 ms (`/api/health`, memory-cached, TTFB 170-190 ms). Production build of feat/chart-mobile in a scratch clone, app API stubbed with 200 ms, Chromium 390px: first load candles ready 0.75 s (1x CPU), 1.3 s (4x); a symbol switch 0.6-1.5 s at 4x, mostly native canvas redraw of 6 panes plus indicator recompute; live ticks ~4% CPU at 4x. Waterfall: `?symbol=BTCUSDT` first fetched SPY's klines, alerts, drawings and quote; drawings for a never-saved ticker went `/api/chart-drawings` → `/api/drawings` in sequence. Code map: every API route calls `supabase.auth.getUser()` (cheap from Ashburn), klines cached 30 s in Redis, Yahoo `withRetry` retries NOT_FOUND, no client cache, `/api/positions` from AppShell + PnLSidebar + every SymbolSelector open, `/api/quote` twice. First Load JS per route 88-330 kB (trading 330).
- L4: the previous chart staying on screen during a switch was dropped: the new asset's drawings would draw over the old asset's candles, and after S2 drawings and alerts arrive in one round trip, usually before the candles. The win is not showing "Cargando…" for an asset seen recently (S4). Found while doing T4: a stock's chart re-polled the full 10-year history every 30 s with a 30 s server cache, so nearly every poll was a fresh Yahoo download; now the history loads once (10 min server cache) and the poll asks a 7-400 day window (30 s).
- L5: app-wide audit (two read-only explorers). Shell: AppShell is mounted per segment layout and fetches `/api/positions` on every section change only for the search's held tickers. Resumen: chart and movements wait for the summary (one round trip later); catalogs fetched every visit; a 1 s countdown re-renders the page in market hours. `/api/positions` miss path ~10 sequential reads plus dolarapi and re-reads the ledger in `currencyViewsFor`; the API never writes `summary:{uid}` and the worker skips off-market, so evenings and weekends always rebuild. `getDerivedSeries` ~12 sequential reads, no single-flight, rebuilt by 4 statistics routes at once on a cold load; statistics/ons and combined download the whole data912 feed uncached (a Redis-first `fetchONQuotesWithFallback` exists); benchmark bars go to Yahoo uncached. Historial refetches per tab; Caja and test portfolio items reload after each edit. Recharts is imported statically (+95 kB statistics, +70 kB ONs). The service worker caches only static assets.
